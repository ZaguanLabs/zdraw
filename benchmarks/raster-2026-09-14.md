# R1/R2 experiment results — 2026-09-14

The bounded native implementation meets the experiment's under-15-ms raster
target on this workstation while preserving the captured reference output.
This establishes a useful acceleration over the supplied Zsh renderer, not
superiority over optimized native graphics libraries or a supported graphics API.

## Reproducible moving-sweep comparison

Environment: AMD Ryzen 9 5950X, x86_64 Linux, public Zsh 5.9.2 source build,
`-Wall -Wmissing-prototypes -O2`, ncurses with `xterm-256color`, `C.UTF-8`.
No installed module or external game repository is needed for this comparison.
The [raw results](raster-2026-09-14.json) include the full platform, every measured
phase, frame counts, output byte counts and hashes.

```sh
export ZSH_BUILD_ROOT="$PWD/.build/sources/zsh-5.9.2"
make test
python3 benchmarks/raster.py --repetitions 5
```

Each backend warms one 12-frame sweep, then measures five sweeps (60 moving
frames). The same captured projected/near-clipped triangles are supplied to both
backends. Times below are mean milliseconds per measured frame in half-block
mode. The total includes shell batch splitting, clearing, phase timing overhead,
packing and presentation, but excludes scene construction/transforms/clipping.

| Pixels | Backend | Submission/raster | Packing + retained drawing | Stage/present | Total |
| --- | --- | ---: | ---: | ---: | ---: |
| 64×32 | Zsh reference | 37.528 | 6.713 | 0.168 | 45.788 |
| 64×32 | Native | 0.119 | 0.024 | 0.148 | 0.850 |
| 96×48 | Zsh reference | 64.570 | 16.044 | 0.223 | 83.118 |
| 96×48 | Native | 0.128 | 0.042 | 0.214 | 0.935 |
| 100×60 | Zsh reference | 78.782 | 22.089 | 0.244 | 103.902 |
| 100×60 | Native | 0.131 | 0.050 | 0.228 | 0.954 |

The native submission/raster phase is about 600 times faster at 100×60 in this
comparison; the whole captured-geometry pipeline is about 109 times faster.
Those ratios are **not game frame-rate multipliers**. At this scale shell data
handling and the application's geometry work matter more than pixel filling.
These are workstation measurements, not latency guarantees or CI thresholds.
The phases are timed around shell calls and should not be interpreted as
isolated CPU instruction costs.

The native and reference half-block runs produce byte-for-byte identical PTY
output at every size (including warmup and cleanup), verified by SHA-256.
Separate two-sweep runs of `--modes ascii mono` also pass exact-output comparison.
The PTY is actively drained. It measures output generation and transport, not
the time a graphical terminal takes to paint pixels.

## Correctness and storage

The fixture contains 36 frames: the original 12-frame camera sweep at 64×32,
96×48 and 100×60. Every native material pixel matches the original Zsh renderer;
inverse depth agrees within 2e-6 absolute/relative tolerance for its eight-decimal
local arithmetic. Additional tests use direct per-pixel barycentrics as an
independent oracle, including 24 deterministically randomized batches of 12
triangles. Crossing triangles, both windings, exact repeated depth ties,
inclusive shared edges, large coordinates, degenerate/offscreen geometry and
captured near-clipped triangles are covered.

A 100×60 surface named `scene` owns 62,270 bytes on this build, including its
double-precision depth buffer, material IDs, fixed palette/pair tables and name.
All allocation is bounded. Readback is diagnostic and allocates shell values;
the frame loop packs directly from native buffers into retained cells.

The complete `make test` suite passes (164 tests), including headless resource
cleanup, malformed input and atomic batch rejection, work/memory bounds,
monochrome and optional narrow/unavailable/failing-color builds, window readback,
odd heights and resize. A Valgrind run of 20 create/draw/resize/read/end cycles,
followed by unload, reports no errors or definite leaks. The updated native
manual also builds successfully with Yodl.

## Supplemental live application checks

An uncommitted adapter under `.build/` connected the native surface to z3dfx's
existing Zsh scene construction, transforms, clipping, HUD and event loop. The
external application sources were not modified and are not build/test
dependencies. These checks are supplemental observations; the self-contained
fixture benchmark above is the repeatable comparison supplied with zdraw.

The same live 12-frame sweep, including world construction/transforms/clipping,
took 104.8 ms/frame with the original renderer and 22.2 ms/frame with native
rasterization at 100×60. Most remaining work is therefore outside the raster
operation.

The game then ran for 90 frames per mode in XTerm 407 on an isolated Xvfb
display, initially 100×35 cells, `xterm-256color`, `C.UTF-8`, with `NO_COLOR`
unset for color testing and the frame cap set to 120:

| Backend/mode | Mean game geometry/raster | Mean game packing/presentation | Reported final fps |
| --- | ---: | ---: | ---: |
| Zsh half blocks | 100.528 ms | 21.180 ms | 8.21 |
| Native half blocks | 24.306 ms | 0.245 ms | 40.67 |
| Native ASCII | 24.862 ms | 0.236 ms | 39.78 |
| Native monochrome | 24.097 ms | 0.214 ms | 41.06 |

All runs exited successfully. The camera in these demos advances with elapsed
time, so different frame rates follow different sampled trajectories; this table
is a practical smoke test, not a controlled same-frame speedup measurement.
Xvfb captures exercise an actual xterm renderer, but do not measure physical
display latency. Captures were inspected for all three native output modes.

A further 180-frame native run, capped at 30 fps, was resized down to the game's
narrow-size message and enlarged again. It recovered its drawing and completed
at a reported 29.5 fps. The adapter used the existing resize/event/presentation
contract; it did not add an input protocol. Initial exploratory captures inherited
`NO_COLOR` and were monochrome; those runs are excluded from the color results
above.

## Limits and decision

The measured benefit is sufficient to retain this as an **experiment**. No
comparison with the strongest relevant external graphics library has been made.
This work does not establish macOS/BSD or alternative-curses portability, a full
terminal/input matrix, or new visual fidelity beyond the existing cells.
ASCII output visibly loses the lower pixel and can have weak contrast with the
game's palette. Half-block appearance remains dependent on the terminal font.

Promotion to a supported API remains subject to the
[recorded quality bar](../docs/scope.md). The experiment stops at bounded flat
triangle filling, native cell packing, diagnostics and explicit presentation.
